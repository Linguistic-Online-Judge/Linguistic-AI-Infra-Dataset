# 固定工作量批处理与内核追踪（2026-09-20）

**结论：32并发将本轮36次德语请求的总耗时从355.12秒降至26.26秒，吞吐提高13.52倍。
短时生成轨迹中的主要开销是矩阵运算；32并发时门控状态更新的占比也明显增加。
但输出与评分发生变化，且同一样本在32并发下出现两种评分，当前不切换线上配置。**

本轮完成用户授权的0号显卡维护实验，原服务已恢复，30人完整评测50秒目标仍未达到。

## 1. 先复核旧证据

重新核验旧8／16／32并发报告的文件摘要后，计算50秒窗口中的客户端在途请求区间：
六组客户端槽位占用均超过99.9%。该实验客户端基本一直维持在途请求，没有明显的
派发空档。但客户端在途可能包含服务端排队，不能据此推断GPU调度占用或算力饱和。

旧德语组包含尾部排空的完成输出速率约为312／513／738词元/秒。各组实际派发和
完成子集不同，不能将这些数值当成相同完整工作量的加速比。只统计50秒内完成请求
得到的词元速率，又会漏掉当时尚未完成请求已经生成的词元。这两种口径都不是纯解码
速率。旧GPU利用率采样中位数虽为100%，也不能证明显存带宽或计算单元已达到上限。

复核文件：`runtime/batch-decode-review-20260920.json`，没有新增模型调用。

- 固定学校Qwen3.5-9B、原消息布局、原输出协议、原评分器、bfloat16精度、4096上下文、

- **正常计时**：单并发与32并发各评测德语HDT冻结清单前6样本×6遍，另各1次预热。
  两组请求集合及参数核对一致。正式计时各36次，共74次含预热请求。
- **单独追踪**：计时结束后，单并发执行第1样本1次；32并发同时执行该样本的32份副本。
  另33次请求。合计107次模型请求，没有写入学生成绩。
- 追踪器已配置但在正常计时期间未启动；追踪期间的耗时不混入正常速度统计。
  配置为延后20个引擎步骤、最多约20步的采集窗口，关闭调用栈、张量形状、内存分析
  及前端追踪。实际两段轨迹各有20个引擎步骤标注。
- 在加载测试模型前，先在已腾出的自有0号显卡上执行微小矩阵运算，确认GPU追踪可用。
  该合成能力检查单独留档，不计作模型请求或性能结果。

已安装PyTorch`2.13.0+cu129`及CUDA性能追踪组件CUPTI`12.9.79`；`nsys`和`ncu`不在
当前PATH中，不据此断言它们在整台服务器上完全不存在。没有安装或升级学校依赖。

两种配置按1→32顺序各启动一次，不是多次进程级随机交错试验。

## 4. 内核时间线

实际步骤标注分别为：

- 单并发：`execute_context_0(0)_generation_1(1)`，20次。
- 32并发：`execute_context_0(0)_generation_32(32)`，20次。

因此这两小段确实采到了没有输入预填充的生成步骤，而非根据延后参数猜测阶段。

| 轨迹内核类别，占所有核函数事件时长总和 | 单并发 | 32并发 |
| --- | ---: | ---: |
| 矩阵乘法/矩阵向量运算，按名称含`gemm`或`gemv`归组 | 95.71% | 79.81% |
| 门控增量状态更新，`gated_delta_rule` | 0.92% | 13.61% |
| 注意力核函数，`flash_fwd` | 0.78% | 3.44% |
| 其他核函数 | 2.60% | 3.13% |

单并发的前两种`ampere_bf16...gemm`占55.83%和28.51%，`gemv2T`约10.99%；32并发的
前两种`cutlass...gemm`占30.70%和21.58%，另有`ampere_bf16...gemm`占18.53%和8.59%。
这里按实际核函数名称分类，不把名字当成硬件带宽或算力计数器。

| 轨迹统计 | 单并发 | 32并发 |
| --- | ---: | ---: |
| 核函数事件数 | 9860 | 10020 |
| 核函数事件时长总和 | 405.536ms | 551.573ms |
| 核函数时间区间并集 | 405.312ms | 551.240ms |
| 首个至最后一个核函数的时间跨度 | 428.324ms | 562.453ms |

新增`kernel_trace.py`以区间并集处理重叠事件，避免把相加时长误当墙钟时间。
上述覆盖率只针对被捕获的核函数，未计入拷贝、清零等事件；不是硬件计算单元占用率，
更不是显存带宽饱和证明。追踪器会改变运行开销，不能用这20步直接宣称正常吞吐上限。

## 5. 输出与重复性

两组逐请求对照：25/36输出摘要不同，12/36评分统计不同。

- 位置1：单并发六遍均为词元编号错误；32并发六遍均可评分，17条弧中2条标签弧正确。
- 位置3：单并发六遍均为2/17标签弧正确；32并发五遍为4/17，一遍为5/17。
- 其他位置评分统计一致，但部分输出文本摘要不同。

本组格式和部分评分有所改善，不能称为质量下降；同一输入在32并发下仍出现不同
评分，也不能宣称已满足可重复性或全任务质量要求。当前不据此改动线上并发和旧合同。

## 7. 后续优化重点

已把主要计算开销定位到生成阶段的矩阵运算，以及较大批次下的门控状态更新。
用户随后明确：平台负责高效组织模型请求并真实反映prompt效果，不以改造模型内部
为目标。因此，本轮内核分析作为耗时诊断证据，后续工作转向平台请求调度、受控并发、
连接复用、输入准备、评分汇总与结果返回，不继续按原先的内部内核/矩阵实现方向推进。

优化需保留学生提交的prompt、既有固定封装、完整50样本、输出与评分合同；不通过
隐藏改写、补充示例、修补模型答案或复用旧成绩代替真实评测来缩短等待或改善分数。
并发方案需同时验证速度和结果可比性，后续端到端检查应包含不同学生prompt，
不能只重复相同提示词后宣称满足真实使用要求。

不把本轮13.52倍提速再叠加到先前32并发结果，也不据此推算必需显卡数量。

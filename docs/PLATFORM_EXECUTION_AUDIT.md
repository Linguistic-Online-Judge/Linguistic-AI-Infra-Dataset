# 平台执行链路审查与首批优化（2026-09-20）

目标：在保持学生prompt、完整样本、既定模型和评分合同的前提下，减少平台的重复处理
与无效等待。本轮检查并修改平台源码，没有调用学校模型、重启服务或部署新版本。

## 1. 当前链路与发现

`提交接口 → 数据库提交/outbox → 按合同路由的队列 → worker认领 → 输入准备/预算检查
→ 逐样本模型调用 → 原评分器汇总 → 完整结果入库 → 网页读取结果`

| 环节 | 代码观察 | 本轮处理 |
| --- | --- | --- |
| 任务调度 | 开发站和统一生产执行器都按任务轮转，一次处理一份完整作业；作业内样本串行 | 保留现有顺序、租约和并发限制；这是后续多用户调度需解决的主要结构性等待 |
| 输入准备 | 每次worker执行均重新解析语料；此前已验证的有界缓存仅能手动传给runner | 接入实际Qwen worker构建路径 |
| 开发站循环 | 每轮处理后固定等待0.25秒，即使这一轮处理了作业 | 与生产执行器已有行为对齐：仅空闲轮次等待 |
| 生产执行器循环 | 已经只在空闲轮次等待0.25秒 | 沿用原行为 |
| 空队列/过期任务检查 | 按合同逐队列接收，每个worker约每5秒执行租约清理 | 本轮未测量70任务扫描的实际延迟；不能把必要恢复检查直接删除 |
| 模型连接 | provider使用标准库HTTP请求，每次调用有线程/超时/终止确认保护 | 连接复用的收益和断连语义尚未验证，不能引入隐式请求重发 |
| 结果显示 | 网页通常每2秒查状态，完成后再读取最终结果；已有换号/换页隔离 | 存在完成后的轮询等待，具体延迟受网络和浏览器调度影响；后续需衡量通知方案与数据库负载 |

逐样本生成仍是重任务的主要耗时。本轮小幅平台优化不能代表30人完整评测50秒目标
已实现，也没有消除整份作业串行造成的队列等待。

## 2. 样本缓存接入

`_SubmissionWorkerCore`、`QwenSubmissionWorker`和测试用`SubmissionWorker`支持显式
`selection_cache`注入，并将同一对象传递给`run_challenge`。

- `qwen_development`和`qwen_executor.build_workers`为一次部署构建共享一份缓存，
  避免70个任务各持有一份完整额度。
- 单任务`qwen_worker.build_worker`为该长期worker持有一份缓存。
- 默认最多16项、8MiB编码载荷；Python对象和副本开销另计，不是进程内存硬上限。
  进程退出后释放，不涉及数据库或评测合同迁移。
- 缓存键为已固定的数据摘要与样本ID顺序。每次使用仍完整核验任务和数据文件摘要；
  冷加载同时核验实际解析的原始字节，返回深拷贝。任务、语言、样本数量和安全输入
  的后续校验照常执行。
- 缓存的是可信所选语料，包括评分数据；模型输入仍只通过既定安全输入构建流程生成。
  学生prompt、模型回答及成绩不进入该缓存。每份评测仍逐样本实际调用provider。

此前独立学校CPU对照中，50样本的准备阶段在暖缓存下节省约英语0.288秒、德语0.562秒。
这些数值来自[既有输入处理实验](INPUT_PROCESSING_RESULTS.md)，不是本轮worker部署后
新测得的端到端收益。冷加载略慢，任务选择频繁淘汰时也可能无法获得暖缓存收益。

## 3. 开发站只在空闲时等待

抽出`_consume_serial_workers`供原生命周期调用，保持原任务轮转和单作业执行：

- 一轮中只要worker实际处理过作业，就继续下一轮，不再固定等待0.25秒。
- 全轮未处理作业时继续保留0.25秒空闲等待，避免空队列忙循环。
- 停止时等待当前作业结束，然后退出，不启动下一作业。
- 发现未确认终止的模型请求时，仍写入原保护标记并退出整个消费循环；原生命周期
  将运行可用性置为失败。该保护不会被缓存或继续轮转绕开。

消除的是每个忙碌**队列轮次**的固定等待，不是每个样本0.25秒，不能将它乘以50
宣称每份评测节省12.5秒。

## 4. 验证了什么

新增两组参数化集成测试分别关闭/开启缓存，经过真实本地API、SQLite、outbox、
队列、Qwen worker预检接口、runner、评分器、最终结果与本人prompt读取接口。
模型响应和分词器使用显式测试替身，身份来自测试认证回调，不是学校模型、正式登录
或30名真实用户的课堂测试。

- 两个测试用户提交不同prompt，包括空白、换行、多语言和Unicode组合字符。
- 每份完整执行50个样本，两份共100次provider调用；缓存不能省略模型调用。
- 发送给provider的请求正文与未使用缓存准备的基线逐字节一致，样本顺序相同。
- fixture按不同prompt分别返回正确/错误标签，最终得分为1/0；prompt原文和摘要准确。
- 用户不能读取对方最终结果；队列为空后的再次运行不会新增调用或成绩。
- 缓存开启时两份作业只解析一次语料，关闭时解析两次；第二份仍重新校验文件摘要。
- 再提交作业并改动语料时，返回原`DATASET_INTEGRITY`失败，不发送新的模型请求，
  不影响已经保存的两个成绩。

开发站测试另确认18个任务共享同一缓存、忙碌轮次不等待、空闲轮次等待、停止时排空
当前作业且不运行下一worker。既有失联阻断、租约、重试及队列恢复测试继续通过。

本机Ruff通过；相关测试75通过，完整回归739通过/33项环境相关跳过。
浏览器、真实数据库和安装包检查以对应提交的持续集成记录为准。

## 5. 部署边界与下一步

这是完成验证的源码修改，尚未更新学校在线应用；此前服务恢复记录与本轮源码验证
应分别看待。实际部署仍需独立安排版本切换及回滚核验。

后续应测量真实多用户的队列等待、认领、输入准备、模型调用、汇总入库和最终显示。
若推进并发调度，必须先完善多请求持久保护、租约及结果归属，再用不同学生prompt
验证结果可比性；不能仅根据此前相同提示词下的32并发吞吐就替换现有合同或上线。

后续已实现有界作业调度、并发请求账本和认领门闩的隔离原型，完整推荐方案与验证边界
见[受控并发方案](BOUNDED_EXECUTION_PLAN.md)。正式入口仍保持原行为。

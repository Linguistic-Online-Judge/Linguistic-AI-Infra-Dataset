# 请求级共享调度：隔离验证

## 1. 本轮目标与边界

整作业内串行时，即使有空闲模型容量，一份德语50样本作业仍可能等待数百秒。
本轮验证`sample_scheduler.py`：让多个独立样本共享有界请求槽位，所有样本完整返回后
仍用原评分器汇总。不改变prompt、模型权重/精度/内核、输出协议或样本数量。

这是隔离的请求层组件，未接入正式提交入口，也没有改变线上调度规则。
调用方必须先确认提交身份、数据和原绝对期限；后续正式集成仍需对接数据库认领、
租约及完成结果的条件写入。当前组件不提供逐样本断点续跑或跨进程作业自动重放。

## 2. 分配与关联

- 优先给在途样本较少的可运行作业分配槽位，相同数量时轮转。
- 只有一份作业时可以使用全部空闲槽位。新作业进入后，在下一可用槽位上参与分配，
  不强制终止旧作业已经发出的请求。
- 每个槽位使用独立provider，整个会话共享同一持久账本。总在途数受模型声明容量、
  账本容量和槽位数共同限制；声明不是实际运行核验。
- `prepare_job`完成全清单和请求预算预检；调度器拒绝重复提交标识、同一用户的另一份
  活跃作业，以及不匹配的模型/生成配置。原型有限会话最多32份作业，不是新增生产额度。
- Future由提交标识和样本位置关联，响应按位置归档；不信任模型响应自带的请求ID。
  按原清单顺序调用原汇总器，未完成作业的结果为缺失，不能补零。

私有请求记录增加可选`request_context`：提交标识摘要、样本标识摘要、位置和实际请求
正文摘要。该字段不进入模型消息，不包含prompt或金标正文。原有无该字段的记录继续
支持；旧代码会拒绝含新字段的记录，因此不能混用旧程序或覆盖已有待确认状态。

本轮控制模式`per_job_limit=1`使用相同输入准备、请求保护和评分代码，但每份作业仅
一个在途样本；共享模式允许借用全部4个槽位。它模拟原作业内串行行为，不等同于
运行完整生产数据库/队列执行器。

## 3. 故障和停止

- 发送前落盘，确认完成后清除自身记录。未知终止继续沿用整组阻断和人工恢复规则。
- 原绝对期限在准备、发送、接收及汇总时检查；等待调度不会重新获得一份新期限。
- 格式错误仍由原评分器记为无效输出。传输失败/超时/关联错误不转换为零分样本。
- 正常停止拒绝新作业，但完成已接受的作业；显式abort或故障停止新样本派发、排空
  已发调用，不发布未完成的成绩。当前原型不自行重试，正式对接需沿用既有合同规则。
- 每个调度会话只能运行一次，重复提交标识不能在同一会话重新执行。

## 4. 本地证据

实际本地HTTP模型替身验证：

- 3种不同prompt各50样本、150个请求，强制第一个样本晚于后续样本返回；每份完整
  汇总与原串行runner完全一致，未完成时没有聚合成绩。
- 校验每次发送前账本中的请求/提交/样本摘要，模型回传伪造请求ID不影响结果归属。
- 单作业达到4个实际并发请求；后来加入的作业得到下一空闲槽位。
- 正常停止完成既有50样本；abort仅排空已发请求。未知断连保留整组记录、阻断重启。
- 截止前未开始的作业没有模型调用，也没有零分成绩；超时返回不发布聚合成绩。
- 错误关联/正文摘要、重复标识、同用户多作业及预检失败均被拒绝。

另以50样本的五类任务fixture核对原评分器聚合一致性。这些是可控模型验证，不能
代表Qwen在并发时的真实输出质量或提速。本机完整回归787通过/35项环境相关跳过。

## 5. 已授权的真实模型对照

用户已授权新的0号显卡维护窗口，预计25–40分钟，最多400次模型请求：

- 在同一个固定4序列容量的Qwen3.5-9B服务上运行，精度和原生成参数保持一致。
- 英语UPOS和德语依存各一份原性能prompt，每份完整50样本。
- 四阶段顺序：串行控制1、共享1、共享2、串行控制2（ABBA），每阶段两份作业同时进入。
- 每模式两次重复，记录完整请求正文摘要、输出摘要、评分统计、各作业可观察完成时间
  和整组时间。保留原300/900秒期限，不加入隐式示例或答案修补。
- 不测试真实网页、认证、数据库/队列等待或30人课堂负载，属于模型请求层校准。

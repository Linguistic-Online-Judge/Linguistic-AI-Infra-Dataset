# 原协议前缀缓存对照（2026-09-20）

**结论：本轮未观察到请求吞吐提升，保持原线上配置。** 英语无缓存命中，德语虽然复用
了部分输入计算，总请求耗时仍未降低；德语输出也不是逐字节完全等价。30人各50样本、
所有最终成绩50秒返回的目标仍未达到。

## 1. 设计与执行范围

用户授权新的0号显卡维护窗口，完成缓存关闭/开启对照后恢复原服务。

- 学校固定Qwen3.5-9B，vLLM发行版本`0.27.1+cu129`，同一RTX3090及驱动。
- 单客户端、服务`max_num_seqs=1`；bfloat16、4096上下文、显存预算0.95、seed2026。
  请求生成参数、原消息布局、原输出协议、提示词、样本和评分器保持一致。
- 两个任务：英语CHILDES词性标注、德语HDT依存分析。各取冻结清单前6个样本、重复3遍，
  每个任务/配置另加1次预热。共4组、72次正式请求+4次预热=76次模型请求。
- 先运行关闭组，再运行开启组；分别启动独立8001测试模型。模型加载及编译不计入
  正式请求时间。相同提示词的重复工作量不等于30个学生，也不是完整50样本验收。
- 关闭：`--no-enable-prefix-caching --mamba-cache-mode none`。
  开启：`--enable-prefix-caching --mamba-cache-mode align`。
  未手动调整块大小、匹配粒度、数值精度或执行内核。
- 使用现有`qwen_performance`持久请求屏障；全部批次完成后确认没有待确认请求。
  请求未进入在线提交接口，未生成新的学生成绩。

这是每个配置一次进程运行的小样本顺序对照，尚未进行多次进程级随机交错实验。

## 2. 速度与缓存命中

| 任务 | 缓存关闭：18次总耗时 | 缓存开启：18次总耗时 | 开启/关闭吞吐比 |
| --- | ---: | ---: | ---: |
| 英语词性标注 | 7.196s | 7.338s | 0.981 |
| 德语依存分析 | 177.607s | 179.136s | 0.991 |

开启后的总耗时分别高约2.0%和0.9%。差异很小，这里只判断“未观察到提速”，
不将其解释为前缀缓存必然降低所有场景的性能。

平均每次请求：英语0.3995→0.4073秒，德语9.8662→9.9511秒。
平均输出长度：英语15→15词元，德语470.5→475.17词元。
德语输出本身发生变化，因此本轮不是固定输出长度下的纯执行内核速度比较。

开启组按模型服务指标的前后差计算，**包含该组1次预热和18次正式请求**：

| 任务 | 查询输入词元数 | 命中词元数 | 词元命中率 |
| --- | ---: | ---: | ---: |
| 英语 | 4228 | 0 | 0% |
| 德语 | 10222 | 3696 | 36.16% |

指标为`vllm:prefix_cache_queries_total`和`vllm:prefix_cache_hits_total`；这是词元比例，
不是请求命中比例或耗时节省比例。关闭组这两个计数均为0，不能以0/0计算命中率。

实际启动日志显示，两组注意力缓存块均自动设为528词元。英语6个请求输入长度仅
220–228词元；德语分别为529、695、518、432、473、584词元。德语3696个命中词元
等于7个528词元块。`align`模式还受状态保存边界约束，不能仅按文本相似度估计收益。

启动日志报告的GPU键值缓存容量：关闭81175词元，开启63780词元。
测量期间整卡显存：关闭组约21268–21368MiB，开启组约21268–21336MiB。
这些是本次配置的观察，不是剩余显存、显卡容量上限或高并发承载证明。

## 3. 输出与评分

| 观察项（各18次正式请求） | 英语 | 德语 |
| --- | ---: | ---: |
| 开关间输出摘要不同 | 0 | 6 |
| 开关间评分统计不同 | 0 | 3 |
| 关闭组格式错误 | 6 | 3 |
| 开启组格式错误 | 6 | 0 |

德语变化集中在两个样本：

- 位置1：关闭组三遍均为`TOKEN_ID_MISMATCH`；开启组三遍可评分，17条弧中4条head
  正确、2条head及关系同时正确。这是格式改善，不能称为句法任务已达标。
- 位置2：三遍输出摘要不同，但评分统计相同，其余样本输出摘要和统计相同。

每个配置内部，每个样本的三次输出摘要及评分统计均一致。重复三次不是三个独立样本，
也不证明跨重启、全语料或跨并发可重复。两种配置分别启停，本轮没有将输出变化进一步
归因于具体缓存命中、`align`执行路径或数值计算差异。

没有修改正式输出协议，也没有应用CPU阶段研究过的JSON字段重排。
当前证据不足以确认全任务质量等价；不基于小样本格式改善启用在线缓存。

## 4. 原服务恢复

维护前实际基线为8个账号、69条成功记录、0个未完成提交，使用新采集的进程身份和
恢复环境，没有复用历史PID作为操作依据。原应用停止后持有其状态目录独占锁，
核对模型空闲及显卡进程归属，再启动测试模型。

测试后已确认：

- 两个测试模型会话均清理，8001测试端口可绑定。
- 原模型恢复到8000、原应用恢复到8090；启动参数和工作目录与维护前完全一致。
- 维护期间及应用就绪后，11张表的数据指纹与基线完全一致，仍为8账号/69结果。
- 在线应用ready，未完成提交为0；在线待确认推理标记和实验持久请求屏障均为空。
- 本轮观察到的新模型服务PID为1581888，应用PID为1583475。未来操作必须重新核验
  进程归属及启动时间，不能直接复用这些PID。

原服务保持单并发、原缓存默认设置；没有发布新的应用源码或改写冻结合同。

首词元延迟和生成阶段速度，定位模型执行开销。当前工具为非流式，尚不能精确分离
预填充、生成和服务内部排队，不能把上述判断写成已测得的阶段耗时比例。

# 32槽位开发站接入与切换准备

## 当前完成范围

开发站现在有显式的请求执行入口：`linguistic_oj.qwen_development --execution-profile FILE`。
它在同一个应用进程中运行网页接口和持续请求执行器，默认准备32个全局样本请求槽位、
4份活跃作业。目录、提交入口和就绪检查直接观察同一个执行器健康状态，无需跨进程
复制就绪标记。本轮未切换学校服务、未重启模型，真实Qwen调用为0。

原无`--execution-profile`的串行入口仍可使用。正式公网`qwen_executor`没有被替换；
这个新入口继续属于私有开发组合，保留原Cookie、开发收件箱和18语言完整目录约束。

## 运行配置版本化

`request_development.py`提供`prepare/check/init`三个命令：

- `prepare`生成新的受保护运行档案，默认`request_slots=32`、`max_active_jobs=4`。
  支持预先准备16请求槽位的候选档，以及4/8/16份活跃作业的隔离对照档案。
- 档案逐项绑定原注册合同摘要，并保存完整执行合同；唯一允许的合同变化是
  `limits.worker_model_concurrency`。prompt封装、模型/分词器身份、生成参数、样本选择、
  评分、额度、重试、期限和来源权利均不能顺带改变。
- `check`重新核对来源及完整档案，不能仅凭手填的并发数字启动。
- 原合同文件、实例`instance.json`和历史成绩不被重写。新提交保存新的执行合同快照，
  历史提交仍保留其原快照；评测身份未修改。这不代表并发间的数值差异已经质量等价。
- `init`在停止应用后显式创建`STATE_DIR/request-executor`。初始化持有原应用状态锁，
  绑定实例、数据库名、队列命名空间、运行档案和模型端点；不能覆盖或重复初始化。

运行档案固定后不可热改。4/8/16对照使用各自隔离状态；修改已经初始化的档案会因
绑定不一致而拒绝启动，不能通过删除账本绕过。上线后的档位切换仍需受控状态迁移。

## 启动与执行保护

1. 读取并验证原18语言目录、数据和运行档案，按原实例所有权规则连接数据库。
2. 若仍有其他合同快照的排队/运行作业，拒绝切换，不把旧作业改判失败或重新写合同。
   SQLite和PostgreSQL使用只读`outstanding_contract_hashes`检查，没有模式迁移。
3. 获取请求账本独占锁；有启动残留、未确认请求或绑定变化时，停止启动。
4. 通过原分词器文件、启动证据和模型别名核验实际声明容量；32档案不能配旧1并发
   启动证据。分词器只加载一次，各合同分别核验，再创建独立样本槽位和原预算预检。
5. 只有执行器进入运行且模型健康时，目录和提交入口才可用。模型暂时不可用时暂停
   新认领和样本派发，既有截止时间持续流逝；历史成绩仍能读取。

新工厂从通过原运行核验的相同HTTP设置构造关联槽位；旧的正式运行核验仍拒绝
`experimental_execution`提供者，没有增加全局绕过开关。这不是对模型实际权重的
加密证明，部署时仍须保存真实启动参数、进程归属和容量证据。

## 停止、监督与恢复

- 正常关闭先停止准入，排空已认领作业；线程结束后才关闭队列并释放账本锁。
  异步等待被取消时，不把取消等待当成模型请求已经结束。
- 执行线程异常会关闭受理状态，并通知应用服务器退出。未知请求/账本故障退出75；
  启动配置或存储配置不符退出78；其他运行故障退出70。
- 新的串行回退入口也检查请求账本。即使数据库已无未完成作业，存在未知请求时
  仍不能绕过请求执行器恢复流程。切回旧版本源码前，操作者同样必须先证明账本清洁。
- 继续使用整组请求恢复：

  ```text
  python -m linguistic_oj.bounded_executor_state status --state-dir STATE_DIR/request-executor
  python -m linguistic_oj.bounded_executor_state recover --state-dir STATE_DIR/request-executor \
      --expected-pending-sha256 EXPECTED --evidence-file PRIVATE_EVIDENCE
  ```

  先确认整组请求终止，审计落盘后才清除；不自动重放模型请求、不恢复内存中的部分成绩。

`scripts/prepare_request_development.py`根据
`config/request_development.example.json`离线生成：

- `execution-profile.json`：来源绑定的运行档案。
- `linguistic-oj-request-development.service`：用户级应用监督模板。
- `initialize-command.txt`：一次性状态初始化命令，不放进日常服务启动命令。
- `preparation.json`：配置摘要和未完成的实际切换事项。
- `request-backup-settings.json`：v2离线备份所需的受保护路径配置。

模板使用`Restart=on-failure`、`RestartPreventExitStatus=75 78`、
`TimeoutStopSec=infinity`、`SendSIGKILL=no`。这避免监督进程通过强杀排空中的作业或
反复重启未知请求来继续发流量。模板只管理应用/执行器；不自动安装服务、打开端口、
启用用户长期驻留或启动/重启模型。

## 混合负载验证

`scripts/check_request_development.py`通过实际`build_qwen_development`入口运行，使用
显式分词器和HTTP模型替身，验证18语言目录、22条任务路由。实际评测工作量包含
英语分词/XPOS/依存/转写与中文UPOS五类任务，并不冒称18语言都做了真实模型评测。

固定32请求槽位，分别设置4/8/16份活跃作业：每组16个Cookie认证账号、16份完整
50样本作业、800次替身请求，实际峰值32。确认：

- 长作业的一个请求仍在途时，后来短作业先完成，成绩可及时读取。
- 不同账号的原始Unicode/空白prompt保持一致；800个提交/样本位置恰好各执行一次。
- 正确与错误的测试prompt分别得到预期的1/0评分，五类任务使用原评分器。
- 健康异常时目录和就绪检查关闭，已有成绩仍可读；退出时队列和账本排空。
- 错误模型容量在生成之前拒绝；初始化不可覆盖；旧作业阻止换档；串行回退不能
  绕过待恢复请求；故障能请求监督退出并保留正确退出码。

学校实际PostgreSQL/Redis三组也全部通过，共2400次替身调用、48份完整成绩，真实

这些是功能与故障保护证据；替身耗时不能用于选择真实Qwen的活跃作业上限。

## 开发站实际切换顺序（尚未执行）

后续已补齐v2离线备份/隔离恢复格式，包含运行档案、请求账本和全部恢复审计，并
通过学校真实数据库及Windows离机验证，见[请求模式备份与恢复](REQUEST_BACKUP_RESTORE.md)。
旧`backup`仍只处理串行v1；请求模式必须使用显式`backup-request`，不能省略新状态。

1. 确定新维护窗口、源代码发布目录、模型32并发真实启动参数与环境、回滚版本。
2. 保存当前数据库、队列、实例标记、原启动环境和历史结果指纹；验证备份可恢复。
3. 停止受理，排空现有作业，确认原未知请求标记和新请求账本均清洁，停止原应用。
4. 安装新源码/档案，核对70合同来源；显式初始化请求账本。单独启动32容量模型并
   保存真实启动证据，再启动新应用监督服务。模型内部和评分规则不变。
5. 验证真实网页提交、完整结果、历史记录和五类任务；以32请求槽位/4活跃作业作为
   初始已测基线。真实4/8/16活跃作业比较需单独固定工作量、测排队期限和评分波动。
6. 若需回退，先停受理、排空并核实账本，再恢复原模型参数和应用。旧新合同快照间
   仍有未完成作业时不得强行切换；不得删除状态或修改旧成绩以解除阻断。

本轮只完成源码接入、隔离验证和切换材料；没有取得或执行新的模型维护窗口。

# 输入处理优化与前缀缓存调查（2026-09-20）

**结论：输入准备可以减少重复工作，但本轮收益不足以实现30人各50样本、全部最终成绩
50秒返回。** 学校CPU离线对照没有调用模型、重启服务或部署优化。当前输出协议保持原样。

## 1. 已实现的优化

- `QwenTokenizerPreflight`在一次预检调用内，对相同学生提示词只单独分词一次。
  每个完整模型请求仍逐条执行聊天模板分词及预算检查；不同提示词分别检查，调用结束
  后不保留提示词或计数。这一优化作用于新源码，学校在线旧源码尚未更新。
- 新增可选`VerifiedSelectionCache`，供`run_challenge(..., selection_cache=cache)`显式
  注入。调用方需在多次评测之间复用同一对象才能获得缓存收益。当前worker、开发服务及
  生产执行器尚未自动接入，不能称为在线缓存已经启用。
  后续已完成worker构建路径的源码接入与隔离验证，见
  [平台执行链路审查](PLATFORM_EXECUTION_AUDIT.md)；学校在线旧版本仍未部署该变化。
- 缓存只保存经过核验的所选语料，包括评分用答案；模型输入仍经原有安全输入构建流程。
  不缓存学生提示词、模型回答或成绩。每次使用都重新核验任务描述和整个数据文件摘要，
  不能仅凭修改时间或文件大小命中。
- 冷加载对解析的实际原始字节同时计算摘要，拒绝校验后数据变化造成的缓存污染。
  保留UTF-8字节顺序标记、通用换行、未选中行校验及重复/缺失样本检查。
- 默认最多16项、8MiB编码后载荷，超限不缓存或淘汰最久未使用项。Python对象及临时
  副本开销另计，因此8MiB不是进程内存硬上限。返回深拷贝，调用方不能修改缓存中的答案。

缓存仍会读取整个文件以核对摘要；它节省的是重复解析、验证和选择样本的部分工作。

## 3. 前缀缓存的可行性与限制

前缀缓存是复用相同输入开头的模型计算状态，不是复用答案。对学校安装的vLLM 0.27.1
源码进行了只读核查，没有构造模型或发起推理：

- `engine/arg_utils.py`：混合架构模型的前缀缓存当前默认关闭，需显式开启。
- `model_executor/models/qwen3_5.py`：明确拒绝`mamba_cache_mode=all`，要求使用`align`。
- `config/cache.py`：`align`只在满足块边界条件的调度步骤末尾保存相应状态。
  `prefix_match_unit`可比物理缓存块更细，但必须整除各组块尺寸；它只改变匹配粒度，
  不改变状态保存频率。不能仅根据公共前缀长度推断实际可复用量。

以上是这台机器安装源码的观察，并非该配置已经启动成功或获得提速的证明。

离线比较原消息布局与“把输入样本字段移至末尾”的候选布局：

| 词元统计（同提示词下的50个样本） | 英语 | 德语 |
| --- | ---: | ---: |
| 原布局：全部请求共同前缀 | 88 | 90 |
| 重排布局：全部请求共同前缀 | 204 | 343 |
| 原布局：平均输入长度 | 227.02 | 545.12 |
| 重排布局：平均输入长度 | 226.20 | 545.24 |

候选仅保证JSON字段值相等，消息字符串及词元顺序不同；**没有发给模型，没有验证
输出或成绩等价，也没有加入正式请求构造**。这些数字不是跨不同学生提示词的命中率，
也不涵盖重复完整输入等其他缓存复用情形。

后续值得单独做原布局下的缓存关闭/开启对照，首先核对实际块配置、命中词元、显存、
吞吐、完整输出评分及重复性。需新的受控模型运行窗口；保留固定模型、原输入/输出
协议和评测设置，按实际启动配置记录证据并恢复服务。字段重排应作为另一项输入变更
单独验证，不能与缓存开关同时改动后归因。CPU阶段当时没有模型侧前缀缓存结果；
后续获准完成的76次原协议对照见[前缀缓存实测](PREFIX_CACHE_STUDY.md)，未观察到提速。

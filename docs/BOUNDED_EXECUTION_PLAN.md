# 平台受控并发方案与隔离原型

## 1. 推荐方案

**后续实测修订**：下述整作业槽位方案已验证执行与故障保护，但主要提高多人总吞吐。
完整实测中德语每份模型调用仍累计约518–609秒，因此它是可靠性基础，不能再作为
足以满足50秒目标的最终方案。结果与后续限制见本文末尾及真实资格报告。

当前已验证的执行基础为**一个统一执行器、少量并发作业、每份作业内按原顺序评测50样本、
完整汇总后发布成绩**。平台组织请求，模型仍按既定配置执行，prompt和评分规则保持不变。

```text
学生提交
  → 认证、幂等与既有额度检查
  → PostgreSQL提交记录与outbox
  → Redis任务队列
  → 统一执行器的有限作业槽位
       每槽：认领一份作业 → 50次原样请求，逐次执行 → 原评分器完整汇总
  → 完整成绩入库
  → 本人结果读取／后续结果通知
```

每个槽位同时执行一份作业、每份作业同时最多一个模型请求，因此J个作业槽位最多有
J个模型请求在途。沿用数据库现有的每用户同时运行上限；当前为1。多个用户可以分享
模型服务容量，而一名用户的一份50样本作业不会一次占用50个槽位。

这能复用既有任务认领、租约、重试和评分核心，比立即拆成可恢复的逐样本分布式任务
更适合当前阶段。任务路由轮转、队列和用户限制保持原有语义；不保证跨任务全局FIFO，
也不抢占已认领的作业。长作业仍会占用槽位，需要在真实多用户负载中计量等待。

## 2. 并发数如何确定

- **线上当前保持1**：现有合同和实际模型服务均声明单并发。
- **先验证2，再验证4**：这是隔离资格测试顺序，不是已经选定的线上配置。
- 不直接采用32：已有实测说明其吞吐更高，但同一prompt出现过不同输出和评分。
- 最终容量需同时受模型实际启动配置、合格评测配置、平台请求上限和资源预算约束。
  不按CPU核心数自动决定，也不因学生数量为30就开30个无约束worker。

并发改变模型的执行批次，仍需测量prompt评分的可比性和重复性。测试必须使用不同
prompt以及相同prompt的重复对照；不可只用同一提示词的工作量副本代替真实用户验收。
允许的评分波动和比较口径需明确确认，不能由实现代码自行放宽。

## 3. 本轮已实现的能力

### 请求账本：`bounded_executor_state.py`

- 使用独立原型状态版本，默认容量1、最多32个在途登记。不读取或自动升级旧串行状态。
- 所有线程共享同一对象，并在整个执行器生命周期持有已有的进程级文件锁。
- 每次发送前生成唯一操作编号，持久记录任务标识和时间；文件刷新、原子替换及目录
  刷新成功后，才允许发起网络请求。不记录学生prompt或模型回答。
- 正常完整响应、或按原provider协议确认已终止的错误，清除自身记录，不清除其他请求。
- 失联、意外异常或写入失败阻断后续派发。发生故障后，其他已在途调用可以结束，
  剩余记录会保守保留供整组核实，可能包含已经收到响应的请求。
- 进程重启时，只要有遗留记录就拒绝继续执行。文件锁释放、租约到期或进程退出均不
  被当作远端模型已结束的证明。
- 恢复必须精确匹配整个待确认集合，先保存审计再清除；错误/缺失/重复证据被拒绝。
  恢复工具不修改学生提交，不发送模型请求，不自动重跑作业。

正常已确认错误仍沿用原合同重试规则；本轮不新增重试。所谓“不自动重发”针对未确认
请求和恢复操作，并不取消已有合同允许的、确认终止后的重试。

### 作业调度：`bounded_dispatch.py`

- 每个槽位拥有独立worker/provider；共享请求账本及已验证样本缓存。
- 检查槽位数、声明容量、worker合同容量；拒绝共享同一provider、混用账本或模型入口。
- 空闲槽位按任务路由轮转，认领一份作业后完成整份；空转轮次有退避，不无限忙轮询。
- 新增可选认领门闩，队列接收和数据库认领与故障阻断共用协调锁。
  门闩已关闭时不取走消息，作业保持queued；锁不覆盖模型生成过程。
- 正常停止不再认领新作业，但完成已认领作业；故障时停止新派发并排空已发请求。
  未完成整份评测的作业不发布部分成绩，原有失败与租约处理路径继续生效。

### 当前隔离边界

这是**可调用、经过隔离测试的原型组件**，不是已经接入学校的并发执行服务：

- `BoundedGuardedProvider`标记为实验执行方式，正式`verify_qwen_runtime`明确拒绝它。
- 现有生产CLI、学校开发循环、旧合同、状态目录和数据库模式没有切换到该原型。
- 原worker核心的认领门闩为可选参数，现有入口默认沿用原行为。
- 原型的`model_capacity`是调用方声明，不能替代模型启动核验；真实接入仍缺完整资格
  配置、生产worker构建入口、实时健康/准入联动及相应部署验收。
- 同机状态锁只协调遵守协议的进程，不会锁住绕过平台直接访问模型的其他程序。

## 4. 已完成验证

### 多用户完整评测

真实本地HTTP模型替身 + 进程内API客户端 + SQLite + 内存队列 + 原worker核心：

- 3个测试用户提交4份不同prompt，每份50样本，共200次HTTP模型请求。
- 测试服务观测到峰值2个并发请求，同一用户始终没有重叠运行。
- prompt中的空白、换行、多语言和Unicode组合字符保持准确；样本顺序一致。
- 模型替身按prompt返回不同标签，最终分别得到预期的1、0.5、0、0.5分。
- 结果和prompt摘要匹配，不能读取其他用户结果；未完成时没有最终成绩。
- 另测早期停止：已认领的2份完整完成100次请求，另外2份仍为queued，没有补零或丢弃。

上述是可控模型/分词器/认证fixture，不是实际Qwen质量、浏览器或30人课堂性能证据。
新的并发组合尚未做学校PostgreSQL/Redis全链路部署验收；既有数据库/队列回归单独保留。

### 故障与恢复

- 并发登记、逆序结束、容量限制和跨进程互斥，没有丢失其他线程的记录。
- 落盘失败时不发送请求；替换后刷新失败，也不能被其他请求结束动作清掉恢复屏障。
- 已确认HTTP错误与未确认断连按原协议区分，失联阻断所有槽位。
- 真实子进程同时发出2个HTTP请求后被强制结束：本地锁释放，但远端测试处理仍在继续；
  新进程被账本阻断。明确确认两个处理均结束后才恢复，观察到没有重发。
- 验证整个待确认集合、证据不匹配、重复恢复，以及审计保存后清除中断的续作。
- 认领门闩关闭时队列消息未被取走；正常停止等待已认领作业而不启动下一作业。
- 正式运行验证拒绝原型provider；错误容量、共享provider和不受保护worker不能启动。

本机Ruff通过，完整Python回归757通过、33项环境相关跳过。远端持续集成结果以本次
提交对应的运行记录为准。

## 5. 原型状态观察与离线恢复

只提供观察和恢复命令，没有连接模型、启动worker或迁移旧状态的CLI：

```bash
python -m linguistic_oj.bounded_executor_state status --state-dir /private/prototype-state
python -m linguistic_oj.bounded_executor_state recover \
  --state-dir /private/prototype-state \
  --expected-pending-sha256 从状态输出复制的集合摘要 \
  --evidence-file /private/confirmed-termination.json
```

路径为示意。确认文件包含`binding_sha256`、按排序列出的全部`pending_request_ids`、
`all_prior_requests_terminated: true`、`confirmed_by`和`evidence_reference`。
操作编号是本地标识，不是模型服务返回的请求编号。人工证据记录终止确认，不自行证明
确认内容真实。必须停止旧执行器后核实整个集合；持有运行锁时恢复被拒绝。

`status`只是瞬时观察，不是就绪判定。正常在途请求也会出现在pending中；未来准入
必须联动执行器故障态和模型健康，不能仅看`blocked`字段或进程锁。

## 6. 分阶段落地顺序

| 阶段 | 内容与完成条件 | 当前状态 |
| --- | --- | --- |
| 平台基础 | 输入复用、空闲等待优化、原样prompt及完整评分 | 源码验证完成，尚未部署 |
| 并发保护原型 | 有限槽位、请求账本、认领门闩、隔离多用户和崩溃测试 | 本轮完成 |
| 真实资格测试 | 独立环境依次测1/2/4，覆盖不同prompt、重复性、完整50样本及长短任务 | 两任务四prompt已完成；有评分波动，尚无正式可比性通过结论 |
| 正式集成 | 合格运行配置与成绩可比性口径、PostgreSQL/Redis组合、故障态准入、部署回滚 | 新组合真实存储/认证已验证，健康准入源码已完成；生产部署待安排 |
| 课堂验收 | 30个独立用户同时提交，各50样本，全部最终成绩在50秒内可读取 | 尚未达到 |

验收分别记录排队、认领/准备、模型请求、汇总入库和网页可见时间。队列受理、进度更新
和提前展示部分结果不能代替最终成绩到达。采集请求账本持久化及数据库开销，避免原型
本身成为新的瓶颈；性能优化仍须保留发送前的持久证明。

若合格并发下单个模型实例仍无法满足目标，再评估获准资源上的同版本模型副本，
并验证跨实例可比性和真实容量。当前证据不足以承诺单卡50秒或给出必需显卡数量，
也不支持通过减少样本、隐藏修改prompt、降低模型精度或替换旧成绩来达标。

后续真实存储/认证验收、维护前模型中断、初次排队超时及质量校准口径调整见
[真实服务验收与模型资格测试](BOUNDED_SERVICES_QUALIFICATION.md)。1/2/4均完成400次
请求和8份完整成绩；不能将受控到达校准称为同时到达压力验收。

后续如评估请求级共享调度，需要让空闲的合格请求槽位服务同一作业的多个独立样本，
并以提交/样本身份关联异步结果，所有50样本完成才汇总。该候选尚未实现或验证，也
不能绕过并发成绩可比性与原有期限。先度量潜在收益，再结合获准资源评估课堂目标；
不继续用整批提速倍数解释每位用户的等待缩短。
